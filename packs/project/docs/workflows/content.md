# Content work

For writing, editing, editorial review, or publishing, first follow the project's
existing content instructions, source documents, audience, voice, approval rules,
and routes. Keep those routes in the root entry when compacting it. The harness
does not supply an editorial policy or authorize publication by itself.

Use existing CONTENT-PLAN, CONTENT-HANDOFF, TASKS, and editorial workflow documents
when present. Do not replace them with generic software milestones. Preserve active
briefs, unresolved factual questions, publication status, and still-active constraints.
Resolve missing acceptance criteria with a targeted question. Check source fidelity,
factual support, audience/format requirements, and requested changes before delivery.

For substantive content changes, use the relevant validation/review stages of
[delivery](delivery.md). Checkpoint and share sanitized content continuity according
to [contracts](contracts.md). Publish or message others only within existing explicit
authorization. Routine read-only editorial questions do not start the full pipeline.
